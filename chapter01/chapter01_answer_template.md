# 3. 실행 성공과 결과 정확성의 차이

## 3-1. SQL 실행 전 예상

학생 A는 질문 2개, 학생 B는 질문 1개, 학생 C는 질문이 없습니다.

```text
전체 학생 수: 3 명
전체 질문 수: 3 개
질문이 있는 학생 수: 2 명
질문이 없는 학생 수: 1 명
```

## 3-2. 임시 테이블 생성 및 데이터 입력 완료 확인

- [ ] `ch01_students` 생성
- [ ] `ch01_questions` 생성
- [ ] 학생 3명 입력
- [ ] 질문 3건 입력
- [ ] 두 테이블의 데이터를 직접 조회

## 3-3. 잘못된 학생 수 SQL 실행 결과

실행한 SQL:

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students AS s
INNER JOIN ch01_questions AS q
    ON q.student_id = s.student_id;
```

실행 결과:

```text
3
```

## 3-4. JOIN 상세 결과 관찰

```text
학생 A가 나타난 행 수:2
학생 B가 나타난 행 수:1
학생 C가 나타난 행 수:0
```

다음 질문에 답합니다.

### Q1. 학생 C가 왜 결과에서 사라졌나요?

```text
inner-join을 통해 입력했었는데, 양쪽 테이블에서 연결되는 행만 남기므로 질문이 없는 학생이 제외된다. 
```

### Q2. 학생 A가 왜 여러 행으로 나타났나요?

```text
한 학생 (A가) 질문을 여러 개 작성해서, 학생도 질문 수만큼 반복되었다. 
```

### Q3. 위 `COUNT(*)`가 실제로 세고 있었던 것은 무엇인가요?

```text
질문을 한 개수에 집중해서 세었다. 
```

### Q4. 결과 숫자가 우연히 실제 학생 수와 같아도 바로 믿으면 안 되는 이유는 무엇인가요?

```text
어떤 과정을 통해 얻어진 결과인지 명확하지 않기 때문에, 우연히 도출된 결과일 수도 있습니다. 
```

## 3-5. 질문 한 건을 추가한 뒤 다시 실행

추가한 데이터:

```text
네 번째 질문이 있는 경우를 추가하였다. (A가 질문을 하나 더 한 경우)
```

다시 실행한 결과:

```text
AI SQL 결과: 질문한 학생 수 4
실제 학생 수: 질문한 학생 수 2
```

### 결과 해석

```text
데이터가 바뀐 뒤 무엇이 달라졌는지: SQL 결과로 도출되는 학생의 수가 달라졌다. 실제 학생 수와 SQL 결과 값이 서로 다르게 나타나서 SQL 값이 올바르지 못함을 쉽게 확인할 수 있었다.

실제 학생 수는 왜 그대로인지: 질문 한 학생 수 (2명)이 찾고자 한 값이기 때문이다. 

이 실험을 통해 알게 된 점: 결과만 확인해서는 이 결과가 정말 믿을만한 결과인지 알 수 없다. 조인 방식 (이너조인인지 아닌지에 따라 null 을 다루는 방식이 달라져서 차이가 발생할 수 있다)
```

## 3-6. 학생 테이블을 직접 센 결과

```sql
SELECT COUNT(*) AS student_count
FROM ch01_students;
```

결과:

```text
3
```

### 두 SQL의 차이를 내 말로 설명

```text
첫 번째 SQL은 질문의 개수에 주목해서 질문한 학생의 수을 세고 있었다.

두 번째 SQL은 질문을 한 학생의 명수에 주목해서 질문한 학생의 수를 세고 있었다.

따라서 SQL을 검토할 때는 문법보다 먼저
도출하고자 한 목적에 적절한 조건으로 작성된 코드인지를 확인해야 한다.
```

# 4. 잘못된 데이터가 결과를 바꾸는 과정

## 4-1. 주문 데이터 확인

다음 데이터를 입력한 뒤 실제 결과를 확인합니다.

```text
ORD-001, 100000
ORD-002, 200000
ORD-002, 200000
```

## 4-2. 실행 전 예상

업무적으로 주문이 `ORD-001`, `ORD-002` 두 건이고 `order_code`가 주문을 고유하게 구분한다고 **가정할 경우** 예상 합계:

```text
300,000 원
```

> 위 가정 자체가 실제 업무 규칙인지 확인해야 한다는 점도 기억합니다.

## 4-3. SQL 합계

```sql
SELECT SUM(amount) AS total_amount
FROM ch01_orders;
```

실제 결과:

```text
500,000 원
```

## 4-4. 결과 해석

### `SUM` 문법 자체가 잘못된 것인가요?

```text
아니요. 주문 번호가 같아서 식별되지 않았기 때문에 중복으로 sum 된 것 뿐, 문법 자체가 잘못된 것은 아닙니다.
```

### 결과 차이의 원인은 무엇인가요?

```text
데이터 자체가 중복되어 있었기 때문입니다. 이를 스스로 잘못된 값임을 판단할 수 없었기 때문입니다.
```

### SQL이 정확하게 실행되어도 업무 숫자가 잘못될 수 있는 이유를 설명하세요.

```text
애초에 데이터 자체의 중복이 있거나, 식별되어야 하는 데이터가 서로 다르게 식별되지 않았기 때문에 잘못될 수 있습니다.
```

## 4-5. AI에게 같은 데이터를 분석시킨 결과

AI가 계산한 합계:

```text
500,000과 중복 가능성을 고려할 때의 300,000을 동시에 언급했습니다. 
```

AI가 중복 가능성을 언급했나요?

```text
네, 코드가 같다는 것을 언급했습니다.
```

AI가 `ORD-002` 두 행이 실제 두 주문인지 중복 입력인지 스스로 확정할 수 있나요? 이유도 적으세요.

```text
아니요. 가능성만 언급할 뿐 스스로 판단하지는 않았고, 결과 값 자체는 500,000으로 제시한 이후 추가 정보로 300,000을 제시했습니다.
```

추가로 확인해야 할 업무 규칙:

```text
1. 데이터가 정확하게 입력되었는가
2. 데이터에 중복이나 누락이 없는가 
3. 내가 표현하고자 하는 바를 잘 반영하는 데이터인가
```

내가 최종적으로 내린 판단:

```text
중복되는 주문은 세지 않는 것이 적절하다. 300,000원. 
```

```text

가장 유용했던 부분: 처음 프로그램을 설치할 때, 비밀번호 입력을 공백으로 두어 설치 오류가 발생해서 곤란했는데, AI 활용해서 비밀번호를 수정할 수 있었다. 

수정하거나 거절한 부분: 첫 실습 과제에서 student_name 이라고 작성된 코드와 그냥 name 이라고 작성된 코드가 같이 있었는데, 오류를 스스로는 발견하지 못했어서 AI 의 도움을 받아 수정하였다. 

그렇게 판단한 근거: 원하는 행이 없다는 오류가 떠서 작성했던 코드를 검토하였다. 

AI가 없었다면 놓쳤을 가능성이 있는 질문: 과제 작성의 시작 과정에서부터 어려움이 있었을 것이다.
```
