# 2. 정규화 전 큰 테이블의 문제 찾기

본문의 `library_records_raw` 구조를 기준으로 생각합니다.

```text
library_records_raw 한 행
→ 대여 사건 한 건이지만 회원·도서의 현재 사실까지 함께 저장된 구조
```

## 2-1. 위험한 중복과 의미 있는 반복 구분

| 반복되는 값/상황 | 위험한 중복 / 의미 있는 반복 | 판단 이유 |
| --- | --- | --- |
| 회원 이메일이 여러 대여 행에 반복 | 위험한 중복이다. | email의 반복은 하나의 사실이 복사되어 행마다 저장되었기 때문에 나타난다. 하나의 회원 정보를 여러 행에 저장하면 이메일 변경 시 여러 행을 수정해야 해서 행마다 값이 달라질 수 있다.|
| 도서 제목이 여러 대여 행에 반복 | 위험한 중복이다. | 제목의 반복은 하나의 사실이 복사되어 행마다 저장되었기 때문에 나타난다. loans에는 book_id를 저장하고, 도서 제목은 도서 테이블에서 조회하는 편이 적절하다. |
| `loans_nf.member_id = 101` 반복 | 의미 있는 반복이다. | 회원 101의 대여 사건을 의미하는 것으로, 회원 101이 여러 대여 사건을 가진다는 관계를 표현하는 것이기에 의미 있다. |
| 사건 당시 가격 같은 이력값 반복 | 의미 있는 반복이다.(사건 당시 값을 보존하는 이력) | 당시의 이력값을 기록하는 것으로, 나중에 가격 등이 바뀌더라도 기록의 가치가 있을 수 있기 때문이다. |

## 2-2. 이상 현상 설명

### 삽입 이상

```text
아직 한 번도 대여되지 않은 새 도서를 등록하려 할 때 생기는 문제: library_records_raw의 한 행이 대여 기록이라고 할 때, 새 도서는 연결할 대여 행이 없어서 독립적으로 등록할 수 없다. 이전에 대여된 적 없는 도서를 관리하기 위해서는 도서 정보를 별도로 관리해야 한다. 
```

### 수정 이상

```text
회원 이메일이 변경될 때 생기는 문제: 김민지의 회원 ID에 해당하는 모든 행을 찾아 수정해야하기 때문에 문제가 된다. 한 행만 수정하는 경우, 이에만 새 이메일이 쓰이고, 나머지에는 행에는 이전 이메일이 기록되어 있기 때문에 어느 이메일이 현재 정보인지 확인하기 어려워진다. 
```

### 삭제 이상

```text
마지막 대여 기록을 삭제할 때 생길 수 있는 문제: 대여 기록과 도서 정보가 한 행에 함께 저장되어 있기 때문에 문제가 발생할 수 있다. 특정 도서가 유일한 대여 행을 가졌던 경우, 이를 삭제하면 도서 정보까지 함께 사라질 수 있기 떄문이다.
```

### 왜 이것이 SQL 문법 문제가 아니라 구조 문제인가요?

```text
SQL의 실행은 이루어지기 때문에 이는 문법의 문제라고 할 수 없다. 문법적으로 정상 실행되더라도, 대여 기록을 삽입, 수정, 삭제하는 과정에서 의도했던 바와 다른 결과가 나타날 수 있다. 이는 업무상 필요한 정보가 손상될 수 있기 때문에 구조 문제이다.
```

# 3. 1NF·2NF·3NF 핵심 질문 복습

정규형 이름만 외우지 말고 **왜 분리하는지** 설명합니다.

## 3-1. 제1정규형(1NF)

```text
한 셀에 쉼표로 여러 독립 값을 넣거나 book1/book2/book3처럼 반복 열을 만들면 왜 문제가 되는가:
각각의 값을 하나씩 검색, 수정하기 어렵다. 예를 들어, 책이나 값의 개수를 바꾸려고 할 때마다 열 구조를 바꿔야 하기 때문에 문제가 된다.
각 책을 독립적으로 관리해야 한다면, 책 만을 별도의 행으로 저장하고, 필요한 경우 다른 테이블의 키로 연결하는 것이 적절하다.
```

내 서비스에서 비슷한 위험이 있는 예:

```text
도시락 정기 배송 회원의 가입 목적을 회원마다 관리하고자 하였다. 이때, 한 회원은 여러 개의 가입 목적을 가질 수 있다고 업무 규칙을 설정하였다. 즉, 한 회원이 여러 가입 목적을 가질 수 있다고 가정하였다. 가입 목적을 한 셀에 여러 개 넣거나 목적1·목적2처럼 반복 열로 저장하면, 비슷한 위험이 발생한다.
```

## 3-2. 제2정규형(2NF)

다음 관계를 설명합니다.

```text
(student_id, course_id) → grade
student_id → student_name
course_id → course_name
```

```text
복합키 전체가 아니라 일부에만 의존하는 열을 분리해야 하는 이유:
(student_id, course_id)가 한 행을 식별하는 복합키인데 student_name은 student_id만으로,
course_name은 course_id만으로 결정된다.
이 값을 수강 행마다 반복 저장하면 학생 이름이나 과목명이 바뀔 때 여러 행을 수정해야 하므로, 학생 정보와 과목 정보를 각각 별도로 관리해야 한다.
```

## 3-3. 제3정규형(3NF)

```text
member_id → zip_code
zip_code → city
```

```text
일반 열이 다른 일반 열을 결정하는 구조를 검토해야 하는 이유:
member_id가 zip_code를 결정하고 zip_code가 city를 결정한다면, member_id를 통해 city가 결정된다.
city를 회원 행마다 저장하면 같은 우편번호의 도시 정보가 여러 행에 반복된다.
city가 우편번호에 직접 의존하는 것이 업무 규칙인 경우, 이를 별도 사실로 분리하여 단순화하는 것이 적절하다. 
```

### 정규화는 값이 반복되기만 하면 무조건 분리하는 것인가요?

```text
아니요. 결정되는 관계가 실제 업무 규칙인지를 확인해야 한다. 또한, 독립적으로 관리해야하는 사실인지를 명확히하고, 분리해야한다. 
분리하기 이전에 각 행의 의미를 살피고, 반복이 업무상 필요한 기록인지 확인해야 한다.
예를 들면, 관계를 표현하기 위해 반복이 필요한 경우나 특정 시점의 값을 기록한다는 점에서 값의 반복이 필요한 경우도 있을 수 있다.
```

# 4. 각 열의 '사실의 주인' 찾기

| 열 | 어떤 사실을 설명하는가 | 주인 테이블 | 이유 |
| --- | --- | --- | --- |
| `member_name` | 회원의 이름 | members_nf | 회원 한 명의 현재 이름을 설명한다. |
| `member_email` | 회원의 이메일 | members_nf | 회원 한 명의 현재 이메일을 설명한다. |
| `book_title` | 도서의 제목 | books_nf | 도서 한 권의 현재 제목을 설명한다. |
| `author` | 도서의 저자 | books_nf | 도서 한 권의 현재 저자를 설명한다. |
| `borrowed_at` | 대여 시각 | loans_nf | 대여 사건 한 건의 발생 시각을 설명한다. |
| `due_at` | 해당 대여의 반납 예정일 | loans_nf | 대여 사건 한 건의 반납 예정일을 설명한다. |
| `returned_at` | 해당 대여의 실제 반납 시각 | loans_nf | 대여 사건 한 건의 실제 반납 시각을 설명한다. |
| `member_id` | 회원의 식별자 | members_nf | 회원 테이블의 pk이다. |
| `book_id` | 도서의 식별자 | books_nf | 도서 테이블의 pk이다. |

정규화 후 한 행의 의미:

```text
members_nf 한 행 = 회원 한 명
books_nf 한 행 = 도서 한 권
loans_nf 한 행 = 대여 사건 한 건
```

### 현재 사실과 사건 당시 이력을 구분하는 기준

```text
값이 지금도 유효한 대상의 정보를 설명하면 현재 사실이고, 사건 당시 이력을 보존하는 값이면 사건 당시 이력이다.
이메일 변경 전 이력도 보존해야 한다면 변경 시점과 이메일을 별도로 기록하는 구조가 필요하다.
```

### 확정되지 않은 정책을 제약조건으로 먼저 만들면 위험한 이유

```text

```

# 9. 정규화와 무결성 제약조건 역할 비교

| 질문 | 나의 설명 |
| --- | --- |
| 정규화가 해결하는 문제 | 같은 사실이 여러 곳에 반복 저장되는 것을 줄여, 수정·추가·삭제할 때 생기는 불일치와 이상 현상을 예방한다. |
| `NOT NULL`이 해결하는 문제 | 반드시 있어야하는 값인데, NULL이 저장되는 것을 막을 수 있다. |
| `UNIQUE`가 해결하는 문제 | 특정 열의 값이 중복 저장되는 것을 막을 수 있다. |
| `CHECK`가 해결하는 문제 | 한 행의 값이 정해진 조건을 만족하지 않으면, 저장되지 않도록 하여 조건에 어긋난 정보의 저장을 막을 수 있다. |
| `FOREIGN KEY`가 해결하는 문제 | 다른 테이블에 존재하지 않는 데이터의 참조를 막을 수 있다. |
| 부분 고유 인덱스가 해결하는 문제 | 조건을 만족하는 행들 사이에서 중복을 막는다. 예를 들면, 미반납 대여가 한 도서에 여러 건 있을 수 없도록 할 수 있다. |

### 정규화만 잘하면 잘못된 데이터가 모두 차단되나요?

```text
아니요. 정규화는 데이터의 중복과 이에 따라 나타날 수 있는 문제점들을 줄일 수 있다. 그러나, 여전히 필수값이 누락되어 NULL 로 기록되는 경우, 존재하지 않는 대상을 참조하는 경우 등 다양한 문제점이 발생할 수 있다. 이를 막기 위해서 NOT NULL, UNIQUE, CHECK, FOREIGN KEY 등 무결성 제약 조건을 적절히 활용해야 한다. 
```

### 제약조건만 많이 넣으면 나쁜 구조가 좋은 구조가 되나요?

```text
아니요. 제약 조건은 정해진 규칙을 따르게 만들어주는 것 뿐이다. 제약 조건이 업무 규칙에 따라 적절하게 부여되어야 한다. 또한 테이블 설정이나 관리할 데이터가 무엇인지, 그 구조를 명확히 하고 이에 필요한 제약조건을 추가해야 한다. 
```
