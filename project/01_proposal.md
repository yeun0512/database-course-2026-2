## 1. 프로젝트 개요

프로젝트 모델 및 개요는 다음과 같습니다. 

### 1-1. 프로젝트 주제

```프로젝트 이름
도시락 정기 배송 회원 영양 관리
```

### 1-2. 비즈니스 모델

#### (1) 비즈니스 모델의 목표
프로젝트를 통해 달성하고자 하는 것은 다음의 두가지 입니다.

```비즈니스 모델의 목표
1. 도시락 정기 배송 회원이 자신의 구입 내역 및 영양소 섭취를 쉽게 확인할 수 있도록 한다.
2. 이용자 별 정기 배송 이용 목적에 적절한 상품 추천을 쉽게 할 수 있도록 한다.  
```

#### (2) 구상 근거
```
도시락 등 식단 상품의 정기 배송 이용자는 건강 관리, 간편 식사 등으로 이용에 있어 뚜렷한 목적을 지닐 것입니다.
정기 배송의 이용 목적은 스스로의 식단을 계획적으로 관리하기 위함일 것이기 때문입니다.
따라서, 꾸준한 내역 관리를 통해 목적 달성률 확인을 지원하는 것은 정기 배송 이용의 만족도를 높일 수 있습니다.
서비스에 대한 만족도 향상은 기존 이용객의 이탈을 줄이고, 신규 이용 유입을 유도할 수 있는 바, 비즈니스 모델이 될 수 있다고 판단하였습니다.
```

### 1-3. 해결하고자 하는 문제

```text
기존의 식단 정기 배송 서비스는 구입 내역만을 관리할 뿐, 사용자에게 그 활용에 대한 지속적인 관리를 제공하는 경우가 많지 않다.
따라서, 본 비즈니스 모델은 사용자의 구입 내역을 고려한 영양소 섭취 실태 및 그 관리를 제공하여 기존 서비스들을 보완하고자 한다.
이를 통해 사용자는 자신의 식단 현황을 쉽게 확인할 수 있을 것이다. 
나아가, 여러 업체의 배송 상품을 비교하고 종합하는 것을 용이하도록 하여 정기 식단 계획 수립에 도움을 받을 수 있을 것이다. 
```

### 1-4. 주요 사용자

```text
긴 호흡의 식단 관리가 필요한 바, 식단 정기 배송 이용자를 대상으로 한다.
정기 배송 이용 목적에 따라 주요 사용자를 다음과 같이 구분한다. 
```

| 사용자 분류 | 이용 목적 | 세부 목적 |
| --- | --- | --- | 
| 개인 | 간편 식사 | 식사 준비 시간 단축 등 |
| 개인 | 건강 관리 | 유아기, 노년기 영양 관리, 체중 조절 등 |
| 단체 | 간편 식사 | 단기간 노동자 식대 제공 등 |
| 단체 | 건강 관리 | 직원 복지 등 |

# 2. 핵심 기능

## 2-1. 주간 식단 배송일 관리

```text
사용자 정보 및 사용자가 선택한 식단과 배송일을 관리한다. 
```

## 2-2. 주간 식단 영양 관리

```text
주간 배송한 식단의 영양 성분 정보를 제공한다. 
(가능한 경우, 월간 요약 정보를 제공한다.
 가능한 경우, 사용자에게 구독한 식단대로 먹었는지, 정보를 받아 목표 달성률 정보를 제공한다.)  
```

## 2-3. 구독 갱신일 관리 
```text
정기 식단의 갱신일 및 결제를 관리한다.
```

# 3. 데이터 구조 및 실현 계획

예상 테이블 및 데이터 구조, 향후 구현 계획입니다. 

## 3-1. 예상 테이블 
```text
예상 테이블: 사용자, 식단 목적, 식단 종류, 식단 제공 업체, 구독, 결제, 배송, 목표 달성, 추천 프로그램, 관심 상품
```

## 3-2. 데이터 구조

### 3-2-1. `members` 테이블

회원 한 명을 관리한다.

| 열 이름 | 저장할 값 | NULL 가능? | UNIQUE 후보? |
| --- | --- | --- | --- |
| id | 회원 고유 번호 (PK) | no | yes |
| name | 회원 이름 | no | no |
| email | 회원 이메일 | yes | yes |
| age | 회원 나이 | yes | no |
| address | 회원 주소 | yes | no |

### 3-2-2. `purpose` 테이블

식단 목적의 종류를 관리한다.

| 열 이름 | 저장할 값 | NULL 가능? | UNIQUE 후보? |
| --- | --- | --- | --- |
| id | 식단 목적 고유 번호 (PK) | no | yes |
| purpose_name | 식단 목적 이름 | no | yes |
| description | 식단 목적에 대한 설명 | yes | no |

### 3-2-3. `member_purposes` 테이블

회원과 식단 목적의 관계를 관리한다. 한 회원이 여러 목적을 선택할 수 있다.

| 열 이름 | 저장할 값 | NULL 가능? | UNIQUE 후보? |
| --- | --- | --- | --- |
| member_id | 회원 고유 번호 (`members.id` 참조, 복합 PK) | no | yes (member_id와 purpose_id 조합) |
| purpose_id | 식단 목적 고유 번호 (`purpose.id` 참조, 복합 PK) | no | yes (member_id와 purpose_id 조합) |
| selected_at | 회원이 목적을 선택한 시각 | no | no |

### 3-2-4. `factory` 테이블

식단 제공 업체 한 곳을 관리한다.

| 열 이름 | 저장할 값 | NULL 가능? | UNIQUE 후보? |
| --- | --- | --- | --- |

### 3-2-5. `item` 테이블

식단 상품 한 종류를 관리한다. 영양 성분은 기준 제공량에 대한 값으로 저장한다.

| 열 이름 | 저장할 값 | NULL 가능? | UNIQUE 후보? |
| --- | --- | --- | --- |

| calories_kcal | 기준 제공량의 열량 | yes | no |
| carbohydrates_g | 기준 제공량의 탄수화물 양 | yes | no |
| protein_g | 기준 제공량의 단백질 양 | yes | no |
| fat_g | 기준 제공량의 지방 양 | yes | no |

## 3-3. 미결정 내용
```
1. 미구독, 만료 회원을 계속 관리할 것인지 결정하지 않았다.
2. 영양 요약은 배송된 식단 기준으로 할지, 실제 섭취 기록 기준으로 할지 결정하지 않았다. 
3. 추천 대상은 구독 식단, 개별 상품 중 어디까지로 하고 어떤 정보를 활용할 것인지, 활용할 것인지 결정하지 않았다. 
4. 구독 갱신 주기와 결제 실패, 등 상황을 어떻게 관리할 것인지 결정하지 않았다. 
```
