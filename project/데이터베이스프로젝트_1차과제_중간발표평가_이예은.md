# 이예은 학생 데이터베이스 프로젝트 1차 피드백

**프로젝트: 도시락 정기 배송 관리 서비스**  
**과목: 데이터베이스**

예은 학생, 여러 업체의 도시락을 비교하고 구독·결제·배송과 영양 정보를 연결하려는 방향이 좋습니다. 회원·업체·상품·구독·배송을 관계형 DB로 구성하려는 11개 테이블과 ERD 초안도 좋은 출발점입니다.

다음 단계에서는 **구독으로 약속한 상품과 실제 배송 품목의 관계, 영양 정보를 계산하는 기준**을 먼저 확정해 주세요. 이를 바탕으로 SQL과 무결성·트랜잭션을 검증하고, 최종에는 실제 DB를 조회·변경하는 웹앱으로 연결해야 합니다.

## 1. 잘한 점

- **사용자 흐름이 연결되어 있습니다.** 상품 비교에서 구독·결제·배송·영양 정보 확인으로 이어집니다.
- **주요 데이터 관계를 구상했습니다.** 회원·목적·업체·상품·배송 상세 등을 나누어 설계했습니다.
- **미확정 항목을 명시했습니다.** 상품 구성, 갱신·결제 실패, 영양 집계와 생산능력을 후속 설계 문제로 남긴 점이 좋습니다.
- **DB 기술을 적용할 업무가 충분합니다.** JOIN·집계뿐 아니라 중복 방지, 상태 관리와 동시 처리의 필요성이 있습니다.

## 2. 우선 보완할 사항

### ① 구독 구성과 실제 배송 내용을 분리해 주세요

한 구독이 한 종류의 상품만 포함하는지, 여러 상품을 조합할 수 있는지 먼저 정해 주세요. 여러 업체의 상품을 한 구독·배송에 묶을 수 있는지도 필요합니다.

| 정책 | 검토할 구조 |
| --- | --- |
| 구독당 단일 상품 | subscription.item_id와 수량·주기의 의미를 명확히 정의 |
| 구독당 복수 상품 | subscription_items 등에 약속한 상품·수량을 별도로 기록 |
| 실제 배송 | shipment와 shipment_items로 출고된 상품·수량을 기록 |

복수 상품을 허용한다면 구독 구성과 배송 상세를 같은 용도로 사용하지 않도록 해 주세요. 품절 대체·건너뛰기·구성 변경이 있어도 과거 배송 사실은 보존되어야 합니다.

상품 가격이 바뀌었을 때 과거 결제금액이 바뀌지 않도록 당시 가격·할인·결제금액의 저장 기준도 정해 주세요. 배송 당시 영양 정보를 재현할 필요가 있다면 상품 영양정보의 버전 또는 스냅샷 정책을 함께 검토하면 좋겠습니다.

### ② 영양 정보의 기준량과 집계 의미를 정해 주세요

현재 nutritions가 상품 정보인지, 회원별 집계 결과인지 역할을 명확히 해야 합니다. 회원당 한 행만 저장하면 기간별 변화를 표현하기 어렵고 계산된 값이 원자료와 어긋날 수 있습니다.

우선 상품별 영양소·단위·기준 제공량을 정리하고 배송 상세와 연결해 기간별 합계를 계산하는 방안을 검토해 주세요. 한 팩 기준인지 100g 기준인지에 따라 배송 수량을 반영하는 식이 달라집니다.

- 상품 영양정보: 영양소, 값, 단위, 기준량·버전
- 회원 목표: 목표 영양소, 단위, 적용 시작·종료일과 일·주 등 기준 기간
- 기간별 집계: 포함할 배송 상태와 날짜, 실제 배송 수량
- 선택적 섭취 기록: 실제 섭취 일자·상품·수량

섭취 기록이 없다면 결과는 **배송된 식품 기준 영양량**으로 표현해 주세요. 실제 섭취·흡수량이나 건강 효과를 측정한 것은 아닙니다. 취소·미배송 건을 집계에서 어떻게 제외하는지도 기록해야 합니다.

목표가 변경되면 과거 주간 결과에 어떤 목표를 적용할지 정하고, 동일 기간 목표의 중복·겹침 정책도 정의해 주세요.

### ③ 키·제약조건과 상태 변경 규칙을 구체화해 주세요

각 테이블의 한 행의 의미와 PK·FK·후보키를 적어 주세요. 회원–목적 연결은 같은 조합이 중복되지 않는지, 배송 상세는 수량이 양수인지 등의 규칙을 검토하면 좋겠습니다.

일반적인 행 단위 제약과 여러 행을 함께 확인해야 하는 업무 규칙을 나누어 주세요.

- 회원·상품·구독·배송 참조: FK와 삭제 정책
- 동일 회원–목적의 중복: 복합 PK 또는 UNIQUE
- 수량·가격·영양값의 허용 범위: NOT NULL·CHECK
- 허용된 결제·배송 상태와 상태 전이: DB 제약과 처리 절차
- 복수 품목의 업체·구독 소속 일치: 관계 설계와 검증
- 생산능력 초과 방지: 동시성을 고려한 트랜잭션

상품·회원이 비활성화되더라도 과거 배송·결제 이력을 유지할지 정해 주세요. 테이블 수를 유지하려고 역할이 다른 사실을 합치거나, 반대로 테이블 수를 늘리는 것 자체를 목표로 할 필요는 없습니다. 대표 테이블 2~3개는 함수적 종속성과 정규화 근거도 설명해 주세요.

### ④ 핵심 SQL과 트랜잭션을 기능에 연결해 주세요

다음 질의에서 최소 3개를 선정해 SQL과 기대 결과를 준비해 주세요.

- 업체·상품·가격·영양정보 비교
- 회원의 구독과 예정 배송 목록
- 배송이 아직 생성되지 않은 구독 조회
- 주간·월간 배송 수량과 영양량 집계
- 업체·날짜별 생산 예정량
- 결제 실패·배송 취소 대상 조회

상품별 영양소가 여러 행이면 JOIN 뒤 배송 수량이나 금액이 중복 합산될 수 있습니다. 사실별 집계 후 연결하는 등 결과가 부풀지 않는지 소표본으로 확인해 주세요. 배송 없는 구독을 보려면 LEFT JOIN의 조건 위치도 점검해야 합니다.

구독 갱신·다음 배송 생성·생산량 배정 중 하나를 원자적 업무로 선정해 주세요. 중간 오류 시 부분 기록이 남지 않는지 확인하고, 같은 요청을 반복해도 배송·청구가 중복되지 않는 기준을 정하면 좋겠습니다.

결제는 학기 프로젝트에서 **성공·실패를 기록하는 모의 처리**로 검증할 수 있습니다. 외부 결제 연동까지 선택한다면 외부 결제 성공과 DB 저장을 하나의 DB 트랜잭션만으로 원자화할 수는 없으므로, 중복 요청과 실패 후 상태 복구를 별도로 설계해야 합니다.

## 3. 2차 제출에서 준비할 내용

1. **업무 정책과 핵심 범위**  
   단일·복수 상품, 복수 업체, 배송 주기, 구성 변경, 갱신·결제 실패·취소 정책을 정리해 주세요.

2. **ERD와 테이블 명세**  
   현재 11개 후보의 역할을 점검하고 필요한 연결 구조를 반영해 주세요. 컬럼·자료형·PK·FK·유일성·필수 관계와 정규화 근거를 제시해 주세요.

3. **영양 집계 정의와 작은 예시 데이터**  
   기준 제공량·단위, 배송 상태·수량, 기간·목표 적용 규칙을 명시해 주세요. 몇 개 상품의 주간 합계를 손으로 계산해 SQL의 기대 결과로 활용해 주세요.

4. **SQL·제약·트랜잭션 검증 계획**  
   대표 질의 3개 이상과 중복·잘못된 참조·수량 오류의 기대 결과를 적어 주세요. 중간 실패와 중복 요청, 생산능력의 잔여량이 적을 때 동시 요청을 어떻게 시험할지도 정리해 주세요.

5. **웹 화면·기술 스택과 구현 계획**  
   PostgreSQL과 연결할 웹 프레임워크를 확정하고, 상품 비교·구독·모의 결제·배송 일정·영양 집계 화면의 DB 읽기·변경 항목을 대응시켜 주세요.

**2차에서는 정책·ERD·대표 SQL과 검증 방법을 구체화하는 것이 우선입니다.** 모든 화면과 외부 결제 연동을 완성할 필요는 없습니다.

## 4. 3차·4차 진행 방향

3차에는 PostgreSQL DDL·시드 자료를 실제 실행하고 PK·FK·UNIQUE·CHECK의 정상·실패 사례를 확인해 주세요. 대표 SQL 결과를 손계산과 대조하고, 구독·결제·배송 관계가 일관되는지도 검증하면 좋겠습니다.

생산능력 제한을 구현한다면 어느 업체·날짜·단위의 한도인지 정하고, 두 요청이 같은 잔여량을 보고 초과 배정하지 않도록 잠금·조건부 갱신 등의 절차를 검토해 주세요. 관련 경로가 같은 규칙을 따르는지 두 세션 시험으로 확인하면 됩니다.

회원별 구독·배송·목표 정보는 다른 회원이 조회·변경할 수 없는지 서버에서도 확인해야 합니다. 업체·관리자 권한과 상품·일정 수정 범위도 구분해 주세요.

인덱스는 회원별 배송 조회, 업체·배송일 생산량 등 실제 질의에 맞춰 선정해 주세요. 같은 데이터와 쿼리에서 EXPLAIN (ANALYZE, BUFFERS)로 전후를 비교하고, 데이터 규모와 실행 조건을 기록하면 좋겠습니다.

4차에는 **상품 비교 → 구독 신청 → 모의 결제 → 배송 일정 → 기간별 영양 집계**가 PostgreSQL을 실제로 조회·변경하는 웹앱으로 이어져야 합니다. 정적 화면만 보여주는 것이 아니라 정상 흐름과 결제 실패·취소·중복 요청·잘못된 권한 사례를 함께 시연해 주세요.

최종 보고서는 **업무 요구사항 → ERD·정규화 → DDL·무결성 → SQL → 트랜잭션·성능·권한 검증 → 웹 연동과 한계**의 흐름으로 구성하면 좋겠습니다. DB 버전, 마이그레이션·시드·실행·검증 순서도 정리해 다른 사람이 재현할 수 있게 해 주세요.

전체적으로 서비스 흐름과 DB 관계를 연결할 기반이 있습니다. 다음 단계에서는 **구독·배송 정책 확정 → 영양 집계 단위 정의 → ERD·제약·SQL → 트랜잭션 검증 → 실제 웹앱 연동** 순서로 진행해 주세요.

*이 피드백은 1차 발표자료에 대한 검토 문서를 바탕으로 작성했습니다. 테이블 후보와 미확정 항목은 기획 내용이며, 실제 DDL·SQL·웹앱 실행 결과는 이후 제출물에서 함께 확인하겠습니다.*
